Multi-Agent Architecture, Part 2: Orchestration — Routing Conversations to the Right Agent

March 21, 2026 · 10 min read

This is Part 2 of the Multi-Agent Architecture series. In Part 1 we covered user interaction — how agents receive and respond to messages. Today we tackle the next question: once a message arrives, how do you decide which agent should handle it?

The Routing Problem

A single-agent system is simple. Every message goes to the same agent, every response comes back through the same path. But the moment you add a second agent, you face a decision that compounds with every agent after it: who handles this message?

In production systems I have worked on, I have seen this solved with nested if-chains, keyword matching, regex dispatchers, and one memorable case where the routing logic was a 400-line function that nobody dared touch. All of these approaches share the same problem — they encode routing decisions as imperative code instead of treating routing as a first-class concern with its own data model.

RoomKit takes a different approach. Routing is declarative, priority-based, and phase-aware. You describe when each agent should activate, and the framework evaluates the rules at runtime.

ConversationRouter and RoutingRules

The central piece is ConversationRouter. You give it a list of RoutingRule objects, each with a target agent, a set of RoutingConditions, and a numeric priority. When an event arrives, the router evaluates every rule in priority order and activates the first match.

from roomkit.orchestration import (
    ConversationRouter,
    RoutingRule,
    RoutingConditions,
    ConversationPhase,
)

router = ConversationRouter(
    rules=[
        # Priority 1: billing questions go to the billing agent
        RoutingRule(
            agent_id="billing-agent",
            priority=1,
            conditions=RoutingConditions(
                intent_match=["billing", "invoice", "payment"],
            ),
        ),
        # Priority 2: technical issues during handling phase
        RoutingRule(
            agent_id="tech-support-agent",
            priority=2,
            conditions=RoutingConditions(
                intent_match=["bug", "error", "not_working"],
                phases=[ConversationPhase.HANDLING],
            ),
        ),
        # Priority 10: catch-all general assistant
        RoutingRule(
            agent_id="general-agent",
            priority=10,
            conditions=RoutingConditions(),
        ),
    ],
)

# Evaluate routing for an incoming event
target = router.evaluate(event)
# Returns "billing-agent", "tech-support-agent", or "general-agent"

A few things to notice. The conditions object supports multiple matching dimensions: intent strings, conversation phases, and arbitrary metadata. An empty RoutingConditions() matches everything — making it a natural catch-all at a low priority. The priority number is evaluated ascending, so priority 1 beats priority 10.

Intent Classification

The router does not classify intents itself — that is not its job. It reads the intent field from event.metadata["intent"] and matches it against the intent_match list in each rule. This means you can use whatever intent classification strategy fits your system: an LLM call, a local classifier, a keyword extractor, or a hardcoded value from upstream logic. The router stays decoupled from the classification mechanism.

In practice, I wire intent classification into a hook that runs before routing. The hook enriches the event metadata, and the router consumes it. Clean separation. If I want to swap from a keyword-based classifier to an LLM-based one, the routing rules stay identical.

Conversation Phases

Not every routing decision depends on what the user said. Some depend on where the conversation is in its lifecycle. A message during intake ("Hi, I need help") requires a different agent than the same message during escalation ("I already explained this three times").

RoomKit models this with ConversationPhase, a lifecycle enum with six stages:

INTAKE --> QUALIFICATION --> HANDLING --> ESCALATION --> RESOLUTION --> FOLLOWUP
  • INTAKE — Initial contact. Collect basic information, identify the user.
  • QUALIFICATION — Determine what the user needs. Classify the request.
  • HANDLING — Active work on the request by the appropriate agent.
  • ESCALATION — The current agent cannot resolve the issue. Transfer to a higher-tier agent or a human.
  • RESOLUTION — The issue is resolved. Confirm with the user.
  • FOLLOWUP — Post-resolution check-in. Satisfaction survey, related offers.

Phase transitions are explicit. An agent or a hook triggers a transition, and the router re-evaluates which agent should be active for the new phase.

from roomkit.orchestration import ConversationPhase

# An agent decides it cannot handle the issue
await orchestrator.transition_phase(
    conversation_id="conv-42",
    new_phase=ConversationPhase.ESCALATION,
    reason="Customer requesting refund above agent's authorized limit",
)

# The router re-evaluates: escalation-phase rules now match
# A senior agent or human operator takes over

The reason parameter is stored in the conversation timeline, so you always have an audit trail of why the conversation moved from one phase to another. This matters when you are debugging why a customer ended up talking to the wrong agent at 2 AM.

The Supervisor Pattern

In a multi-agent system, you often need one agent that always knows what is happening — regardless of which specialist is currently active. RoomKit supports this through the supervisor_id parameter.

When you designate an agent as supervisor, it receives every event in the conversation, even when it is not the active agent. The active agent handles the user-facing response; the supervisor observes, logs, and can intervene when necessary.

The supervisor pattern solves a class of problems that are hard to address with pure routing: quality monitoring, compliance checks, SLA enforcement, and graceful degradation when a specialist agent fails. The supervisor is always watching, always receiving context, and always able to step in.

Non-active, non-supervisor agents are muted — they do not receive events and do not consume resources. This keeps the system efficient even with dozens of registered agents.

Handoffs: Agent-to-Agent Transfers

Routing handles the initial assignment, but conversations are not static. A billing agent might discover the user actually has a technical problem. A general agent might realize the question requires a specialist. The user might explicitly ask to "talk to someone else."

This is where HandoffHandler comes in. A handoff is a structured transfer from one agent to another, with context injection so the receiving agent does not start from zero.

from roomkit.orchestration import HandoffHandler, HandoffConfig

handoff = HandoffHandler(
    config=HandoffConfig(
        # Inject conversation summary into the receiving agent's context
        inject_summary=True,
        # Include the last N messages for immediate context
        context_window=10,
        # Notify the user that a transfer is happening
        announce_transfer=True,
        announcement_template="Transferring you to {target_agent} for further assistance.",
    ),
)

# Execute the handoff
await handoff.transfer(
    conversation_id="conv-42",
    source_agent="general-agent",
    target_agent="billing-agent",
    reason="User asked about invoice discrepancy",
    metadata={"invoice_id": "INV-2026-0847"},
)

During a handoff, the handler does several things: it mutes the source agent, activates the target agent, optionally generates a summary of the conversation so far, injects that summary plus the last N messages into the target agent's context, and sends an announcement to the user. The metadata dictionary lets you pass structured data — an invoice ID, a ticket number, a customer tier — so the receiving agent can act immediately without asking the user to repeat themselves.

This is the difference between a handoff that frustrates users ("Can you explain your issue again?") and one that feels seamless ("I see you have a question about invoice INV-2026-0847. Let me look into that.").

Sequential Workflows with ConversationPipeline

Not all multi-agent scenarios are about routing to one agent or another. Some workflows are inherently sequential: an intake agent collects information, a qualification agent classifies the request, a specialist handles it, a resolution agent wraps up. Each agent does its part, then passes the conversation forward.

ConversationPipeline models this as a series of PipelineStage definitions. Each stage specifies an agent, an optional phase, and transition conditions. The pipeline advances automatically when a stage's exit criteria are met.

from roomkit.orchestration import ConversationPipeline, PipelineStage

pipeline = ConversationPipeline(
    stages=[
        PipelineStage(
            agent_id="intake-agent",
            phase=ConversationPhase.INTAKE,
            exit_condition="user_identified",
        ),
        PipelineStage(
            agent_id="qualification-agent",
            phase=ConversationPhase.QUALIFICATION,
            exit_condition="intent_classified",
        ),
        PipelineStage(
            agent_id="specialist-agent",
            phase=ConversationPhase.HANDLING,
            exit_condition="issue_resolved",
        ),
        PipelineStage(
            agent_id="followup-agent",
            phase=ConversationPhase.FOLLOWUP,
        ),
    ],
)

The pipeline approach works well when the conversation has a predictable shape. For more dynamic scenarios — where the next agent depends on runtime conditions — the ConversationRouter with priority-based rules is the better fit. In practice, I often combine both: a pipeline for the overall structure, with routing rules that handle exceptions and escalations within each stage.

Fallback Behavior

What happens when no routing rule matches? Or when the active agent crashes? RoomKit handles this through two mechanisms.

First, the supervisor agent (if configured) always receives events. Even if routing fails completely, the supervisor can respond. It acts as a safety net — the agent of last resort that keeps the conversation alive while the system recovers.

Second, every non-active agent is muted by default. This means a routing failure does not accidentally broadcast a message to every agent in the system. Only the active agent and the supervisor see events. If the active agent becomes unresponsive, the supervisor can trigger a handoff to a fallback agent or escalate to a human operator.

This is a deliberate design choice. In a multi-agent system, silence is preferable to chaos. A user waiting a few seconds for a supervisor to pick up is a better experience than three agents responding simultaneously with conflicting answers.

Putting It Together

The orchestration layer in RoomKit is the connective tissue between agents. It answers three questions at every point in a conversation:

  1. Who handles this? — ConversationRouter with priority-based RoutingRule evaluation.
  2. Where are we? — ConversationPhase lifecycle with explicit transitions and audit trails.
  3. What happens when things change? — HandoffHandler for agent-to-agent transfers, ConversationPipeline for sequential workflows, and supervisor oversight for safety.

None of these components require you to use the others. You can use ConversationRouter alone if your routing needs are simple. You can add phases later when your workflows demand it. You can wire in handoffs only for the agent pairs that need them. The pieces compose without coupling.
